Three production systems from the same insurer: the problem, the decisions, and what changed. The decisions are filed as public notices at the foot of this section.

Case Study No.1

Owned the technical design and build of the platform across policy, claims, and agent workflows.

Result90,000+ clients in production · 6 engineers in parallel · 0 breaking API changes

Monolith to ModularRBACOWASP
+
Challenge

Legacy monolithic insurance platform could not scale, had no API layer, security was bolt-on, and adding features meant touching everything. 90,000+ clients depended on it daily.

Approach

Defined bounded contexts using domain-driven design. Drew service boundaries around underwriting, policy admin, claims, and agent management. Designed API-first contracts with versioning. Implemented RBAC with Duende IdentityServer (OAuth2/OIDC, BFF pattern, reference tokens).

Key Decisions
  • Phased migration, monolith to modular monolith to service-ready, instead of a big-bang rewrite Notice No. 1
  • YARP as the API gateway: lightweight and .NET-native Notice No. 2
  • Domain-driven bounded contexts with explicit integration contracts
  • OWASP Top 10 aligned security controls at every layer
  • One RBAC model on Duende IdentityServer for 5,000+ agents, 85,000+ customers and internal operations Notice No. 3
  • API versioning with a backward-compatibility policy: zero breaking changes
Outcome

Phase one shipped: a modular monolith behind a YARP gateway, IdentityServer, API-first contracts, the whole client base in production, and six engineers working in parallel without stepping on each other. New features ship without full regression. Phase two, extracting cloud-ready services, is the 2026 transformation mandate.

Case Study No.2

Execution-plan driven performance engineering across the insurance data layer, with timeouts cut from 12+ a week to under one.

ResultQuery latency −50% · timeouts 12+ a week → under 1

Execution plansCovering indexesOracle + SQL Server
+
Challenge

Insurance platform's database layer was the bottleneck. Premium calculation engine timing out during peak loads. Query response times degrading as data grew. DB CPU regularly hitting 90%+.

Approach

Ran a systematic database performance audit, captured execution plans, identified missing/redundant indexes, found expensive table scans in stored procedures, and mapped query patterns against actual workload.

Key Decisions
  • Rewrote the critical stored procedures from cursor loops to set-based statements
  • Redesigned the indexes around the measured query patterns, with covering indexes for the hot queries Notice No. 5
  • Fixed parameter sniffing patterns where applicable
  • Verified every change against execution plans and IO and time statistics
  • On the .NET side: DTO shaping to stop over-fetching, async with cancellation tokens, connection pooling
  • Defined SLOs and monitoring dashboards so regressions are caught before they are reported
Outcome

Query latency halved, which took the premium calculation engine across 20+ product lines off the peak-hour bottleneck.

Case Study No.3

Designed and built the payment flow end to end: zero duplicates, near-real-time reconciliation, full auditability.

Result0 duplicate transactions · reconciliation 2 days → near real time · audit prep 2 weeks → 1 day

Idempotency keysState machineImmutable audit log
+
Challenge

Premium collections, policy payouts, and agent commissions all ran through one payment flow. It had no reconciliation and no idempotency, and failures were tracked in spreadsheets.

Approach

Designed end-to-end payment gateway integration with a “nothing gets lost” principle. Mapped every transaction state, idempotency, reconciliation patterns, and complete audit trail logging.

Key Decisions
  • An idempotency key on every payment request, so a retry can never double-charge Notice No. 4
  • A payment state machine: Initiated, Authorized, Captured, then Settled, Failed or Refunded
  • Webhook and callback flows with retries, exponential backoff and circuit breakers
  • Automated reconciliation comparing gateway records with internal state
  • Audit logging for regulatory compliance: immutable logs, correlation IDs
  • Security: tokenization, avoid storing PAN, least privilege, secret management

Public Notices

Decision record · five entries
  1. No. 1

    Phase the migration; no big-bang rewrite

    Decision
    Move the platform from a monolith to a modular monolith first, behind an API gateway and one identity server, and extract cloud-ready services in a second phase.
    Context
    90,000+ clients depended on the legacy platform daily. It had no API layer, security was bolt-on, and six engineers needed to ship features in parallel while it was rebuilt.
    Rejected
    A big-bang rewrite, which stops feature delivery for the business while it runs.
    Consequences
    Phase one shipped: a modular monolith behind YARP and IdentityServer with API-first contracts, and features ship without full regression. Service extraction is the 2026 transformation mandate.

    Accepted · in productionCase Study 1 →

  2. No. 2

    YARP as the API gateway

    Decision
    A YARP reverse proxy in front of the bounded contexts, kept in the same .NET solution and pipeline as the modules.
    Context
    A .NET team, API-first contracts with versioning and a backward-compatibility policy, and one deployment pipeline to keep.
    Consequences
    The gateway is lightweight and .NET-native, and routing rules live beside the contracts they serve, under the same code review.

    Accepted · in productionCase Study 1 →

  3. No. 3

    Duende IdentityServer with a BFF and reference tokens

    Decision
    OAuth2 and OIDC through Duende IdentityServer, the BFF pattern for the browser clients, and reference tokens rather than self-contained ones.
    Context
    One RBAC model for 5,000+ agents, 85,000+ customers and internal operations, with OWASP Top 10 controls at every layer.
    Consequences
    Tokens stay server-side behind the BFF and can be revoked at the server; one identity model serves the portal, the API and the digital channels.

    Accepted · in productionCase Study 1 →

  4. No. 4

    Idempotency keys and reconciliation, both

    Decision
    An idempotency key on every payment request, a state machine with six states (Initiated, Authorized, Captured, Settled, Failed, Refunded), and automated reconciliation against the gateway's records.
    Context
    Premium collections, policy payouts and agent commissions ran through one flow with no reconciliation and no idempotency; failures were tracked in spreadsheets.
    Why both
    A key prevents a duplicate but cannot see drift between the gateway and the ledger; reconciliation alone finds a duplicate only after the money has moved.
    Consequences
    Zero duplicate transactions; reconciliation from two days to near real time; failed-payment recovery from days to minutes; audit preparation from two weeks to one day.

    Accepted · in productionCase Study 3 →

  5. No. 5

    Fix the queries and the indexes before anything else

    Decision
    Rewrite the hot procedures from cursor loops to set-based statements and redesign the indexes around the measured query patterns, every change verified with execution plans and IO and time statistics.
    Context
    The premium engine timed out at peak across 20+ product lines, database CPU sat at 90%+, and timeouts ran at 12+ a week.
    Consequences
    Query latency roughly halved; timeouts under one a week; SLOs and dashboards in place for regression detection; DTO shaping and async work on the .NET side.

    Accepted · in productionCase Study 2 →

04 Open Source

After hours: grahan,
a sky engine on npm

grahan (ग्रहण, “eclipse”) is a zero-dependency TypeScript engine for astronomy, panchang, and the Bikram Sambat calendar. I learned TypeScript and npm from scratch to ship it, and wrote the reference answers before the formulas.

What it computes

Sun and Moon positions, sunrise and sunset, moon phases, and solar and lunar eclipses from 1900 to 2100. On top: a full panchang (tithi, nakshatra, yoga, karana, Rahu Kaal), birth charts, dashas and muhurta, and Bikram Sambat conversion for BS 1975–2200.

How it is verified

Fixtures come from Swiss Ephemeris 2.10 first, and the formulas are written to match them: 279 tests from Singapore to the Arctic. Sun longitude lands within 4.6″, and every one of 909 eclipses is detected and typed exactly. The first test case was my own birth chart, cast by a jyotishi decades ago. It matches.

How it ships

Strict TypeScript and pure functions that run in Node 18+, browsers, and edge runtimes; the panchang engine is under 10 KB in a browser. Releases publish from CI through npm trusted publishing with signed provenance, so no long-lived token exists to leak. My day-job .NET is proprietary; grahan is the public sample of how I test and release.
